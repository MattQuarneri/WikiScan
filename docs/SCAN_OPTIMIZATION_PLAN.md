# WikiScan Scan Optimization — Implementation Plan

**Repo:** MattQuarneri/WikiScan · **File under review:** `wikiscan.rs` (1,639 lines, `main` @ `ecfd5a1`)
**Verified:** 2026-10-04 against the live repo (source + `Cargo.toml` fetched via GitHub API). Every finding below was re-checked line-by-line; nothing unverified is included.
**Constraint (explicit):** No full-decompression strategy. The dump stays compressed on disk; all wins must come from scanning the compressed form smarter.

---

## How to use this document (agentic development)

Each item is a self-contained work unit: **OPT-00 … OPT-07**, in dependency order. An agent should:

1. Take exactly one OPT at a time, in phase order (Phase 0 first — it gates everything).
2. Run the Phase 0 benchmark **before** and **after** the change; attach both numbers to the PR/commit message.
3. Pass the item's acceptance criteria (behavior-preserving: identical match sets on the fixed test fixture) before moving on.
4. Stop and report if an acceptance criterion fails — do not "fix" a mismatch by changing expected output.

**Global acceptance rule (applies to every OPT):** On the fixed test fixture (see Phase 0), the set of `(title, member_offset)` matches for the benchmark keyword must be **byte-identical** before and after the change, unless the OPT explicitly documents an intended semantic change. Performance claims without before/after numbers do not count as done.

## Phase 0 — OPT-00: Benchmark harness (do first, gates all other work)

**Why:** Every other OPT claims a speedup. Without a fixed fixture and a repeatable measurement, "faster" is unfalsifiable and regressions are invisible.

**Deliverables:**

1. **Fixed test fixture:** a small, deterministic dump slice committed outside the repo (or generated by script): e.g. the first N members of a real multistream dump, or a synthetic `.xml.bz2` built from a handful of known pages. Must include: pages that match the benchmark keyword, pages that don't, a page with XML-escaped characters in text (`&amp;`, `&lt;`), and at least one non-ASCII title.
2. **Benchmark keywords:** one common (`"the"`-class, many matches), one rare (few matches), one containing an XML-escapable character (e.g. `"R&D"`) — the third exists specifically to protect OPT-06.
3. **Harness:** a script (shell or a `#[ignore]`d integration test / example binary) that runs index build on the fixture and reports, per run:
   - wall-clock seconds
   - pages scanned, matches found
   - peak RSS (e.g. `/usr/bin/time -v` on Linux)
   - checksum of the sorted `(title, offset)` match list (this is the behavior-preservation gate)
4. **Baseline record:** run it on the unmodified code; paste the table into the PR description and into a `BENCHMARKS.md` (or the PR thread) so later OPTs diff against it.

**Acceptance criteria:**
- [ ] Harness runs end-to-end on a clean checkout with one command.
- [ ] Two consecutive baseline runs produce identical match-list checksums.
- [ ] Baseline numbers (time / pages·s⁻¹ / matches / peak RSS) are recorded.

**Risks:** Fixture too small → timing noise dominates. Mitigate: fixture sized for a ≥10 s baseline run, or run the keyword scan 3× and report median.

## Phase 1 — OPT-01: Remove the per-member index save 🔴 Critical

**Severity:** Critical (correctness-adjacent performance bug — the code does the opposite of what its own comment says).

**Location:** `build_keyword_index`, ~L1257–L1275.

**Problem (verified):** Inside `for off in offsets.drain(..)`, after every member:

```rust
// Update in-memory map; persistence handled by periodic save   (~L1258)
idx_map.insert(title.to_string(), off);
...
// Persist checkpoint to disk to survive crashes or restarts   (~L1271)
let _ = save_keyword_idx(&idx_map, &out_file);                  // ← EVERY iteration
// Periodic durable sync
if last_sync.elapsed() >= Duration::from_secs(15) {             // ← the intended mechanism
    let _ = save_keyword_idx(&idx_map, &out_file);
    last_sync = Instant::now();
}
```

`save_keyword_idx` (~L1568) does `File::create` + rewrites **every** `(title, offset)` line in the map. A multistream dump has tens of thousands of members, so this is tens of thousands of full-file rewrites, each more expensive than the last as the map grows. The 15-second checkpoint directly below it — clearly the intended design — is rendered pointless.

**Draft resolution:**

1. Delete the unconditional per-iteration `save_keyword_idx` call (~L1271).
2. Keep the 15-second timed checkpoint. Optionally add an every-N-members checkpoint (e.g. N=50) as a second trigger if crash-loss granularity matters more than the timer gives.
3. Keep the existing saves on cancel and on normal completion (~L1282) untouched.

**Tradeoff (state it in the commit message):** A crash now loses at most the checkpoint window (~15 s of scanning) instead of ~one member. The existing resume logic (load `.idx`, skip processed members) already tolerates this — that is what the checkpoint design was for.

**Acceptance criteria:**
- [ ] Match-list checksum on the fixture is identical to baseline.
- [ ] Index file on disk after completion is identical to baseline output.
- [ ] Kill the process mid-scan; restart; resume completes and produces the identical final index.
- [ ] Benchmark: report before/after wall-clock. Expect this to be the single largest win on large-match-count keywords.

**Risks:** Minimal. One subtlety — `ticker.tick` and the checkpoint share the loop tail; make sure removing the save doesn't remove the tick.

## Phase 2 — OPT-02: Allocation-free case-insensitive match

**Severity:** High.

**Location (verified, three sites):**
- `build_keyword_index_mem` ~L389: `text.to_lowercase().contains(&kw_lower)`
- `filter_index_with_keyword` ~L429: same pattern
- `build_keyword_index` ~L1256: same pattern

**Problem:** `to_lowercase()` builds a brand-new `String` the size of the full page text, for every page scanned, purely to run a substring test. Across a full dump that is gigabytes of transient allocation and copying — pure overhead on the hot path.

**Draft resolution (pick one, in order of preference):**

1. **Preferred, no new dependency:** compile the matcher once per scan —
   ```rust
   let re = regex::RegexBuilder::new(&regex::escape(keyword))
       .case_insensitive(true).build()?;
   // per page: re.is_match(text)
   ```
   `regex` is already in `Cargo.toml`. Compile once outside the member loop and pass it (or a small `KeywordMatcher` struct) into the handlers. Note: current semantics are *literal* substring on lowercased text; `regex::escape` preserves literal semantics.
2. **Alternative (multi-keyword future):** add `aho-corasick` with `.ascii_case_insensitive(true)` — SIMD-accelerated, and it pays off more if multi-keyword search ever lands.
3. **Alternative (zero-dependency):** a small hand-rolled ASCII-folding `memmem` helper. Only choose this if avoiding regex overhead is demonstrably needed; Unicode case-folding differences vs `to_lowercase()` must be documented.

**Semantics warning (must be addressed in the PR):** `to_lowercase()` does full Unicode lowercasing. Options 1–3 differ subtly on non-ASCII text (regex `case_insensitive` does Unicode folding; ASCII-insensitive matching does not). The fixture's non-ASCII title/page (Phase 0) exists to catch this. Whichever option is chosen, state the resulting semantics in a code comment: matching is defined as *X*.

**Acceptance criteria:**
- [ ] Match-list checksum identical to baseline on the fixture, including the non-ASCII case — or any difference is explicitly documented as an intended semantics change and called out for human sign-off.
- [ ] No `to_lowercase()` remains on the per-page hot path (title-only lowercasing elsewhere, e.g. REPL filter ~L981, is out of scope).
- [ ] Benchmark: report before/after wall-clock and peak RSS.

**Risks:** Regex compile cost per scan is trivial (once). Regex matching on huge texts can be slower than `contains` for very short literal keywords in pathological cases — the benchmark decides; if regex regresses the common-keyword case, fall back to option 2/3.

## Phase 3 — OPT-03: Parallel member processing (+ stop reopening the file)

**Severity:** High. **This is the largest structural change; do it after OPT-01/02 are in.**

**Location (verified):**
- `visit_pages_in_member` ~L1109: `File::open` + `seek` on **every** call.
- Member loops are sequential: ~L387 (`build_keyword_index_mem`), ~L425 (`filter_index_with_keyword`), ~L1251 (`build_keyword_index`).
- `Cargo.toml` already declares `memmap2 = "0.9"` — and `grep` confirms it is **never used** anywhere in `wikiscan.rs`.

**Problem:** Bzip2 member decompression is CPU-bound and members are fully independent, yet the scan runs on one core and pays an open+seek syscall pair per member.

**Draft resolution:**

1. Add `rayon` (see Dependency changes). Convert the offset loops to `par_iter()`, with per-thread results collected and merged (each thread builds a local `HashMap`/counters; merge at the end — no shared mutable map on the hot path).
2. I/O strategy, two acceptable shapes (benchmark both if time permits):
   - **Simple:** one `File` handle per rayon thread (thread-local), seek per member as today.
   - **Preferred:** mmap the dump once with the already-declared `memmap2`, hand each worker a `&mmap[offset..]` slice, and construct the `BzDecoder` over that slice. No per-member syscalls at all.
3. Bound memory: worker count = rayon default (core count); each worker holds one member's decompressed buffer at a time.

**⚠️ Correctness caveat — resume watermark breaks (must handle):** `build_keyword_index` resumes by computing `existing_max_off` (max offset in the existing `.idx`, ~L1228) and skipping all members `<= existing_max_off` (~L1238–1245). That assumes members complete **in offset order**. Under parallel, out-of-order completion means the max-offset watermark can claim members were processed when they weren't — silently losing matches on resume.

   **Required fix, pick one:**
   - **(a)** Replace the watermark with an explicit **completed-offset set** persisted alongside the index (e.g. a sidecar file of finished member offsets, or derive completed-ness differently); resume skips exactly that set. More bookkeeping, fully correct.
   - **(b)** Keep the resumable on-disk path (`build_keyword_index`) sequential for now; parallelize only the in-memory paths (`build_keyword_index_mem`, `filter_index_with_keyword`, REPL `search=`) where no resume state exists. Ship (b) first, then (a) as a follow-up if the on-disk path still needs the speed.

   Option (b) is the recommended sequencing: it captures most of the win with zero resume-correctness risk.

**Acceptance criteria:**
- [ ] Match-list checksum identical to baseline (parallel merge must not drop or duplicate entries — assert deterministic output regardless of thread count; test with `RAYON_NUM_THREADS=1` and `=8`).
- [ ] If option (a): kill-mid-scan + resume test from OPT-01 still passes, and a targeted test where completion is deliberately out of order resumes correctly.
- [ ] Benchmark: report scaling at 1/2/4/8 threads (pages·s⁻¹). Expect near-linear until decompression or I/O saturates.
- [ ] Cancellation (`Q`) still stops the scan promptly (rayon workers must check the cancel flag per member, as today).

**Risks:** `HashMap` merge contention if implemented naively (avoid: thread-local maps). mmap of a multi-GB dump is fine on 64-bit; document that the mapping is read-only and the file must not be truncated mid-scan.

## Phase 4 — OPT-04 + OPT-05: Header scan (fallback path only)

These two only affect the fallback flow when no multistream index exists (`find_bzip2_member_offsets`, called ~L372, ~L813, ~L1199). Bundle them: they touch the same function.

### OPT-04: SIMD candidate scan

**Severity:** Medium. **Location:** `find_bzip2_member_offsets` ~L246–310 (verified: 1 MiB chunks, per-byte `tmp[i]==b'B' && tmp[i+1]==b'Z' && tmp[i+2]==b'h'` checks, with a duplicated code path for the carry/boundary case).

**Draft resolution:**
1. Add `memchr` (see Dependency changes). Use `memchr::memchr_iter(b'B', chunk)` to jump between `B` candidates and check the following 3 bytes (`Zh` + `1..=9`) only at candidates.
2. This collapses the two duplicated branches (carry / no-carry): keep the 3-byte carry for boundary safety, but drive both through the same candidate loop.
3. Optional, only if the benchmark says the header scan still matters: shard the file into N ranges (with 3-byte overlap) and scan shards in parallel with rayon, then sort+dedup offsets (already done at ~L309).

**Acceptance criteria:**
- [ ] Candidate offset list identical to baseline on the fixture (before validation — compare the raw candidate sets).
- [ ] Boundary case tested: a `BZh9` header straddling a chunk edge is found exactly once.
- [ ] Benchmark: header-scan phase timed separately before/after.

### OPT-05: Delete the header-validation pass

**Severity:** Medium. **Location:** `find_bzip2_member_offsets` ~L312–350 (verified: reopens the file, then per candidate does `seek` + `take(64 KiB)` + `BzDecoder` probe read of 1 byte).

**Problem:** An entire second pass over every candidate, with a seek and decoder setup each, just to learn whether the offset decompresses at all.

**Draft resolution:**
1. Delete the validation pass; return candidates directly.
2. Rely on the consumers, which already tolerate bad members: `build_keyword_index` logs `warning: skipping member @ …` and continues (~L1267). Audit the other consumers (`build_keyword_index_mem`, REPL search ~L873) and add the same warn-and-skip where a hard `?` would now abort a scan on a bogus offset — this audit is part of the task, not optional.
3. Where a real multistream index exists, it is already authoritative; nothing changes there.

**Tradeoff:** A bogus offset now costs one failed member decompression attempt during the scan instead of one 64 KiB probe during validation. Failed bzip2 decodes error out fast on a bad header, so this is roughly cost-neutral per bad offset — and it removes a full pass over the good ones.

**Acceptance criteria:**
- [ ] End-to-end match-list checksum identical to baseline (bogus offsets produce warnings, not aborts or phantom matches).
- [ ] A fixture containing a planted fake `BZh9` byte sequence inside compressed data scans to completion.
- [ ] Benchmark: fallback-path total time before/after.

**Risks:** If any consumer currently *depends* on pre-validated offsets for correctness (not just robustness), the audit in step 2 must find it. The grep surface is small: all `visit_pages_in_member` callers.

## Phase 5 — OPT-06: Decompress-then-prefilter per member

**Severity:** Medium. **Do after OPT-02** (the prefilter reuses the same matcher).

**Location:** `visit_pages_in_member` ~L1100–1167 (verified: decompressed bytes stream straight into quick-xml; every member is fully XML-parsed).

**Problem:** XML parsing is paid for every member even when the keyword appears in none of its ~100 pages. For a rare keyword, that's nearly all of the parse cost wasted.

**Draft resolution:**

1. Restructure per-member work into two steps:
   - Decompress the member once into a `Vec<u8>` buffer.
   - Run the OPT-02 case-insensitive matcher over the raw buffer. **No match → skip XML parsing entirely.** Match → parse the buffer with quick-xml as today.
2. This implies a sibling of `visit_pages_in_member` that operates on an in-memory buffer rather than opening the file itself — which composes naturally with OPT-03's mmap slices.

**⚠️ Correctness caveat — false negatives (the plan's hard rule):** The raw decompressed buffer contains XML-escaped text. A keyword containing an XML-escapable character can appear in source as an entity — `R&D` is stored as `R&amp;D` — so a raw-buffer search for `R&D` **misses a real match**. False positives are harmless (they just get parsed); false negatives are silent data loss.

   **Safe rule (implement exactly this):**
   - If the keyword contains **none** of `& < > ' "` → raw prefilter is safe, use it.
   - If it contains **any** of them → bypass the prefilter and parse every member (current behavior).
   
   The `"R&D"` fixture keyword from Phase 0 exists to prove this rule works. Add a unit test: page text `R&amp;D` + keyword `R&D` must match, with prefilter enabled.

**Acceptance criteria:**
- [ ] Match-list checksum identical to baseline for **all three** benchmark keywords, including `"R&D"`.
- [ ] Unit test for the escapable-character rule (both branches).
- [ ] Benchmark: biggest expected gain on the rare keyword; report per-keyword before/after.

**Risks:** Peak memory rises by one decompressed member per worker thread (bounded, typically a few MB × thread count). Under OPT-03, account for this in the RSS comparison.

## Phase 6 — OPT-07: Micro-fixes in the XML text path

**Severity:** Low. Opportunistic — fold into any phase that already touches these functions.

**Location (verified):**
- `visit_pages_in_member` ~L1146–1149: `e.unescape().unwrap_or_default()` called per `Event::Text` (allocates a `Cow`/String each event; called up to 3× per event across the title/id/text branches). Duplicated logic at ~L1385–1389 and ~L1532.
- `build_keyword_index` ~L1257: `existing.insert(title.to_string())` followed by `idx_map.insert(title.to_string(), off)` — the title is cloned twice for one insert.

**Draft resolution:**
1. Accumulate the raw (still-escaped) text per page and unescape **once** when the page closes, instead of per text event. (quick-xml may split one logical text run into multiple events; per-event unescape is both slower and more allocation-heavy.) Keep behavior identical for the page-id parse.
2. Clone the title once: `if existing.insert(title.to_string()) { idx_map.insert(title.to_string(), off) }` → bind one owned `String` and reuse it (or restructure with the entry API).

**Acceptance criteria:**
- [ ] Match-list checksum identical to baseline; page text extraction (`get_page_text` path) byte-identical on fixture pages, including one with entities split across events if constructible.
- [ ] No benchmark regression (gain expected to be small; this item is justified on allocation reduction, not headline speed).

**Risks:** Text-event splitting semantics — verify against quick-xml 0.31 behavior on the fixture before generalizing the change to all three duplicated sites.

## Sequencing summary

| Phase | Items | Why this order |
|-------|-------|----------------|
| 0 | OPT-00 harness | Nothing lands without before/after numbers |
| 1 | OPT-01 | One-line-class fix, likely the biggest single win, zero risk to matching semantics |
| 2 | OPT-02 | Removes per-page allocation; matcher is reused by OPT-06 |
| 3 | OPT-03 | Parallelism; sequenced as in-memory paths first (option b), resumable path second (option a) |
| 4 | OPT-04 + OPT-05 | Same function, fallback path only; independent of 1–3, can move earlier if the fallback path is the user's common case |
| 5 | OPT-06 | Depends on OPT-02's matcher; hard correctness rule for escapable keywords |
| 6 | OPT-07 | Opportunistic micro-fixes |

Expected cumulative effect (to be replaced by measured numbers as phases land): OPT-01 removes an O(n²)-ish disk cost; OPT-03 should scale throughput roughly with core count; OPT-02 + OPT-06 remove most allocation and parse work for non-matching content. None of this requires decompressing the dump to disk.

## Non-goals

- **Full decompression of the dump** — explicitly out of scope per the user's constraint (disk cost). All optimizations operate on the compressed dump in place.
- Changing index file formats (`title\toffset` lines) or REPL command surface — except the possible completed-offset sidecar in OPT-03 option (a), which must be called out for human sign-off before implementation.
- Multi-keyword / boolean search — noted only as context for the OPT-02 matcher choice.
- Replacing bzip2 or the multistream format.

## Follow-on note (not a phase)

The REPL currently risks rebuilding scan state per command: `find_bzip2_member_offsets` is invoked from multiple REPL paths (~L813, ~L372). Once OPT-03 lands the mmap + offset table, the REPL session should **cache the mmap and member-offset table across commands** (compute once per `W=` dump selection, invalidate on dump change) instead of re-deriving them per search. Small, safe, and a natural cleanup after Phase 3 — file it as a post-plan issue rather than expanding OPT-03's scope.
